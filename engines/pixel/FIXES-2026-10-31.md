## 1. P0 · 点击「假成功」：注入被系统忽略时仍报 `expect 匹配 ✓`

**现象（2026-10-31 12:55–12:57）**
右鼠标键卡在按下状态（`GetAsyncKeyState(VK_RBUTTON)` 为 down）+ 系统无前台窗口（`GetForegroundWindow()` 返回 0）时，Windows 忽略所有注入点击。

- `mouse_click {x:361,y:741, expect:{titleContains:"ima"}, verify:"text"}` 连续 3 次返回：
  `已点击 … / 目标窗口: ima / 点击后前台: (无窗口) / 验证: expect 匹配 ✓`
- 页面毫无变化；同样位置用 PowerShell `SetCursorPos + mouse_event` 点击也无反应；**把右键强制 `mouse_event(RIGHTUP)` 释放后，同一个点击立刻生效并完成导航**（`GetAsyncKeyState(0x02)` 变 False，`GetForegroundWindow()` 变 `ima`）。
- 同期的 `mouse_scroll` **照常生效**（滚轮不受影响），所以问题只出在点击路径。

**根因（两处）**
1. `index.js:2568-2576` 的点击后验证拿错了对象：
   ```js
   if (expectCheck.checked) {
     const postExpect = checkExpect(window2, args.expect)   // ← window2 是点击前的目标窗口常量
   ```
   它重新校验的是**点击前的 `window2`**，等于自证清白；真正的 `fg`（第 2567 行取的 `post.foreground`）只被打印，从不参与判定，`fg === null` 也不报警。
2. 点击前没有检查「输入通道是否可用」：helper 的 status 里其实**已经有 `buttonsDown`**（`runtime/helper.cs:1996` 附近 `CurrentButtonsDown()`），但没有用于点击前预检；`DoClick`（`helper.cs:2644`）发完 `SendInput` 就返回成功，不校验系统是否真的处于可接收输入的状态。

**建议改法**
- `mouse_click` 点击后验证改为：
  - `fg` 为 null/`handle===0` → `outcome='clicked-no-foreground'`，正文明确写 **「点击可能未生效：系统当前没有前台窗口（常见于鼠标键卡住/输入被忽略）」**，并附 `buttonsDown`。
  - `expectCheck` 用真实 `fg` 比对，不一致就是 mismatch（现在的 `window2` 判据保留为附加信息即可）。
- 点击前预检（新增，成本≈0）：`statusData()` 里 `buttonsDown` 非空 → 直接返回「疑似鼠标键卡住（L/R/M 具体哪个）」并建议先 `mouse_abort`；`fg` 为 null → 警告但仍可尝试（记录 `note`）。
- `screen_info` 已有 `buttonsDown` 展示（`index.js:1513`），确认它**永远**输出该行（现在只在非空时输出，卡键发生时我在 `screen_info` 里没看到，才多绕了 4 步）。
- `helper` 侧：`DoClick` 在 `SendInput` 前后各取一次 `GetCursorPos/GetForegroundWindow`，把 `foregroundBefore/After` 回传，Host 侧据此判定"点击是否可能被吞"。

**验收**
1. 手测：按住鼠标右键不放（或脚本 `mouse_event(RIGHTDOWN)`），再 `mouse_click` → 必须报失败/警告，**不得**出现 `验证: expect 匹配 ✓`。
2. `npm test` 新增 host 用例：mock `status` 返回 `foreground:null` → 断言 outcome 不是 `clicked`。
3. 正常场景回归：`npm run test:helper` 59/59 仍全绿。

## 2. P0 · `window_focus` 基本无效，却只回「已请求聚焦（helper 未确认）」

**现象**：对 `ima`（pid 11648）连续调用 `window_focus` 两次，都返回
`已请求聚焦（helper 未确认）: "ima" …`，`screen_info` 里前台仍是 DSH；最后靠 `mouse_click` 点标题栏、再靠外部 PowerShell `WScript.Shell.AppActivate(11648)` 才切过去。批量动作之后前台还会悄悄跳回 DSH。

**代码位置**
- `index.js:2258-2270`：`state.helper.rpc('focus', …)` 之后只区分 `data.focused === false`，文案软化，没有重试、没有原因、没有"失败"语义。
- `runtime/helper.cs:~890-950`（`DoFocus`）：`ShowWindow(SW_RESTORE)` + `SetForegroundWindow`，失败后用 `AttachThreadInput` 再试一次，两次都失败就返回 `focused=false`。已在用标准手法，说明**失败原因是前台锁**（当前前台进程不同 / 注入来源被认为是后台）。

**建议改法**
- helper：失败时回传 `lastError`、`foregroundTitle`，并再补一轮 `AttachThreadInput(前台线程, 自己线程)` + `BringWindowToTop` + `SetWindowPos(HWND_TOP, SWP_NOMOVE|SWP_NOSIZE)` 组合；仍失败则明确返回 `focused:false, reason:"foreground-lock"`。
- Host：`focused===false` 时**不要**只写"未确认"，写成失败并给可执行替代：
  「聚焦失败（前台锁）。可先 `mouse_click` 点目标窗口标题栏（一次点击=激活），再继续；或让人类手动切换。」
  并附 `expectAfter` 建议（点击标题栏后校验前台标题）。
- 增加「点击标题栏自动激活」的小工具或参数：`mouse_click {activateOnly:true}` 点窗口标题栏（不构成新风险，仍走授权/审计）。

**验收**
- 当 DSH 是前台时调用 `window_focus(ima)`：要么真的切过去（`screen_info` 显示前台=ima），要么返回明确失败原因；不允许"未确认"式含糊。
- `npm test`：mock `focus` 返回 `focused:false` → 断言文本包含"失败"与替代方案。

## 3. P1 · `mouse_abort` 会把授权一起清掉（常开也清）

**现象**：为排查 P0 调了一次 `mouse_abort`，返回「授权窗口已清除」；本会话审批策略是 `never`，从此插件**完全无法注入**，只能改用 PowerShell，实验的对照性被破坏。

**代码位置**：`index.js:3813-3823`，`state.gate.disarm('mouse_abort')` 是无条件的；工具描述（3816 行）也写明会清授权。

**建议改法**
- 语义拆开：`mouse_abort` 只做「释放按键 + 中断在飞动作」；新增参数 `keepArm`（默认 `true`？——**建议默认 false 保持兼容，但文档写清楚**）。
- 更稳妥：提供 `releaseKeys`（只释放不改授权）与现有 `mouse_abort`（保持旧语义）两个入口，或 `mouse_abort {disarm:false}`。
- 如果前一状态是 `latched`（常开），abort 后**自动恢复 latched** 而不是彻底清零。
- 返回文案里必须写清楚「授权是否保留」，当前只写"已清除"。

**验收**：`mouse_abort` 后 `screen_info` 仍显示 `常开授权`（当且仅当 `keepArm` 未显式关闭），且能继续注入。

## 4. P1 · `screen_read` 不总省 token；`query` 命中不足会**静默退化成小图**

**现象**
- 60 元素的全量导出 = 3,102 字符 ≈ **1.0–1.5k token**，和一张 1600×1023 截图（插件自报 **1,072 图 token**）基本打平 → "文本一定更省 token"在元素密集窗口不成立。
- `screen_read {query:"费用明细", maxElements:5}` 因命中 2 < `minElements=3`，**直接退回 720×460 截图（281 token）**，既不返回命中的 2 个元素，也不在标题里给 token 估算。

**代码位置**：`index.js:2091-2103`（命中不足分支）、`index.js:2165`（回退截图行）、`:2009`（`minElements` 描述）。

**建议改法**
- 命中不足时**先返回命中的元素**（哪怕 1 个），并在正文写「命中 N 个，低于 minElements，未截图；如需像素细节加 `allowImageFallback:true` 或放宽 query」。
- `query` 存在时，**默认不自动回退截图**（退回的成本与精度都差）；保留 `allowImageFallback` 显式开关。
- 输出头统一带 `≈N tokens` 估算（`screen_capture` 已有该字段，`screen_read` 没有）。
- 回退图仍保留，但正文标注「已退化：文字读取失败，改用 X×Y 小图（低细节）」——现在只写"已退回截图"。

**验收**
- `query` 命中 2 个元素时返回这 2 个元素 + 提示，不产生图片；`allowImageFallback:true` 时才出图。
- host 用例：断言无 `query` 命中不足 + `allowImageFallback` 未传 → 不出图。

## 5. P1 · 滚动没有"内容是否移动"的反馈

**现象**：`口令.txt` 只有一屏、**根本不可滚动**；我用 2 个 `mouse_batch`、24 个滚动动作（每次 delta 20）全部打空，返回都是 `✓`，没有任何"画面未变化"提示（截图有 captureHash 去重，滚动没有）。

**代码位置**：`index.js:2754-2830`（`mouse_scroll`）、`mouse_batch` 的 scroll 分支。

**建议改法**
- 每个 scroll 动作前后，对光标附近小区域（如 120×120）取一次 captureHash（helper 已经支持 capture，成本极低）：
  - 连续 2 次 scroll 后 hash 不变 → 结果里标注「⚠️ 内容未变化（可能已到边界，或该区域不可滚动）」。
  - batch 汇总行追加 `noMove:N`。
- 可选参数 `detectNoMove`（默认 true）。

**验收**：在不可滚动区域滚 3 次 → 返回里出现"内容未变化"；在列表里滚动 → 不出现该提示。

## 6. P2 · 覆盖层状态含糊（排障成本高）

**现象**：排查点击失效时，`screen_info` 显示 `overlay=available=true visible=true`，我一度怀疑全屏覆盖层吞点击，专门 `matrix_overlay show=false` 复测——无效（真因是 P0 的卡键）。`overlayMode=auto` + 常开授权时覆盖层到底是否可命中（hit-testable）在状态里看不出来。

**建议改法**：`screen_info` / `/click-matrix status` 增加一行 `overlay: visible=true hitTestable=false`（用 `GetWindowLong(GWL_EXSTYLE) & WS_EX_TRANSPARENT` 判定），并在 doctor 里同步。

## 7. P2 · `screen_read` 偶发多行/异常尺寸框

**现象**：面包屑出现 `"如何找到知识库及引擎口令" 尺寸 121x128`、`"IMA引擎工作区" 尺寸 110x80`（文字被折行成多行框），不影响点击，但会误导"中心点"判断。

## 9. 不要做的事（安全边界）

- 不要为了"点击成功率"绕过人工授权、窗口黑名单、UIPI 检查；P0 的修复方向是**把失败暴露出来**，不是硬试。
- 不要用 `Stop-Process`/`taskkill` 处理 helper 异常；helper 有 `helperTimeoutMs` 自杀重建。
- 不要在 `mouse_click` 里悄悄重试（会掩盖问题、也可能重复点击）；如需重试请给显式参数并逐次审计。
- 中文文件只用 `write`/`edit`/Node 修改，不要用 PowerShell `Get-Content`→`Set-Content` 往返。
